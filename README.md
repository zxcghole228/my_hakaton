# E-CUP 2026: матчинг товаров

Репозиторий содержит материалы обучения, построения и запуска трёх кандидатов семейства USER-BGE-M3 для задачи матчинга товаров E-CUP 2026.

Основная цель репозитория — зафиксировать происхождение моделей, параметры экспериментов, результаты, контрольные суммы артефактов и код, необходимый для воспроизведения обучения и inference-only solution.

|  2 | [Stage-B v2 checkpoint soup](versions/bge/02_stage_b_v2_checkpoint_soup_8515/README.md)                   | Объединение двух Stage-B checkpoint           | `0.5520634383301408` |
|  3 | [Stage-B v3 cross-soup с symmetry TTA](versions/bge/03_stage_b_v3_cross_soup_symmetry_tta_5540/README.md) | Cross-checkpoint soup и симметричный инференс | `0.5539900397479464` |

Полный перечень кандидатов находится в [`versions/bge/registry.json`](versions/bge/registry.json).

## Постановка задачи

Для каждой пары товаров необходимо оценить вероятность того, что оба идентификатора относятся к одному товару.

Runtime получает:

* таблицу товаров `items.parquet`;
* таблицу пар `matches.parquet`;
* путь для сохранения результата.

Ожидаемый результат содержит столбцы:

```text
id1,id2,predict
```

Runtime должен сохранить все входные пары, исходный порядок строк и повторяющиеся пары.

## Развитие решения

### Кандидат 1: baseline

Первый кандидат получен дообучением открытой предобученной модели `deepvk/USER-bge-m3` на базовом корпусе матчей.

Это baseline fine-tuning предобученной модели, а не обучение BGE со случайно инициализированными весами.

Кандидат не использует:

* checkpoint soup;
* ансамблирование нескольких моделей;
* symmetry TTA;
* дополнительный Stage-B этап.

### Кандидат 2: Stage-B v2 checkpoint soup

Второй кандидат продолжает baseline-направление с использованием ручной разметки, LLM replay и Stage-B обучения.

Финальные параметры модели получены по формуле:

```text
0.15 × step_00400.pt + 0.85 × step_02000.pt
```

После объединения checkpoint используется одна модель и один прямой проход для каждой пары. Symmetry TTA на инференсе не применяется.

### Кандидат 3: Stage-B v3 cross-soup и symmetry TTA

Третий кандидат объединяет checkpoint из двух Stage-B запусков:

```text
0.83 × Stage-B v2 step_02000.pt
+
0.17 × Stage-B v3 step_00400.pt
```

На инференсе применяется symmetry TTA: модель оценивает оба порядка товаров, после чего вероятности усредняются.

## Структура репозитория

```text
.
├── versions/
│   └── bge/
│       ├── README.md
│       ├── registry.json
│       ├── 01_base_bge_m3/
│       ├── 02_stage_b_v2_checkpoint_soup_8515/
│       └── 03_stage_b_v3_cross_soup_symmetry_tta_5540/
├── data/
├── artifacts/
├── final/
├── requirements/
├── tests/
├── tools/
└── docs/
```

Каждая версия может содержать:

* `README.md` — описание эксперимента и ограничений воспроизводимости;
* `version.json` — параметры обучения, метрики, lineage и сведения о весах;
* `training/original/` — исходные notebook и training-файлы;
* `training/reconstructed/` — восстановленный исполнявшийся код;
* `runs/` — метрики, логи и результаты выбора checkpoint;
* `construction/original/` — исходный сборщик submission;
* `construction/runtime/` — исправленный воспроизводимый сборщик;
* `solution/original/` — неизменённый snapshot полученного solution;
* `solution/runtime/` — исправленный runtime;
* `artifacts/manifest.json` — размеры, SHA-256 и статус артефактов;
* `recovery/` — восстановительный snapshot исходных материалов.

## Original и runtime

Для сохранения происхождения файлов исходный и исправленный код разделены.

`solution/original` содержит solution в том виде, в котором он был получен от автора модели и использовался при подготовке исходного submission.

`solution/runtime` содержит исправления контракта и воспроизводимости:

* поддержку аргументов как с дефисами, так и с подчёркиваниями;
* локальную загрузку модели без сетевых запросов;
* сохранение всех входных строк;
* обработку отсутствующих товаров и пустых текстов;
* сохранение исходного порядка и повторяющихся пар;
* формирование выходного столбца `predict`.

Leaderboard score относится к исходному отправленному solution. Для исправленного runtime тот же score не заявляется без отдельного запуска на площадке.

## Базовая модель и лицензия

Все три кандидата основаны на открытой модели [`deepvk/USER-bge-m3`](https://huggingface.co/deepvk/USER-bge-m3), опубликованной под лицензией Apache-2.0.

Точная ревизия базовой модели, использованная во время исходного обучения, не была записана. Репозиторий явно фиксирует её статус как `not_recorded` или `missing` и не подменяет неизвестное значение предположением.

Inference-код загружает модель из локальной директории и не требует проприетарных API или сетевых сервисов.

## Данные

Большие датасеты соревнования не хранятся в Git.

В зависимости от кандидата для воспроизведения используются следующие локальные файлы:

* `items.parquet`;
* `items_human.parquet`;
* `matches.parquet`;
* `matches_llm.parquet`.

Названия, назначение и известные размеры выборок зафиксированы в `version.json` соответствующих кандидатов.

Репозиторий не выполняет дополнительную скрытую разметку и не обращается к внешним LLM API во время обучения или инференса.

## Веса и большие артефакты

Файлы `*.safetensors`, `*.pt`, `*.pth` и другие большие артефакты не добавляются в Git.

Для финальных весов каждой модели зафиксированы:

* размер файла;
* SHA-256;
* локальный путь;
* связь с кандидатом;
* статус доступности;
* необходимость для сборки solution.

Эти сведения находятся в:

* `versions/bge/registry.json`;
* `version.json` каждой версии;
* `artifacts/manifest.json` каждой версии.

Отсутствующие исторические checkpoint не выдаются за сохранённые: они явно отмечены статусом `not_collected`.

## Воспроизведение обучения

Для воспроизведения конкретного кандидата необходимо:

1. Открыть README выбранной версии.
2. Подготовить перечисленные локальные датасеты.
3. Проверить окружение по `training/environment.json`.
4. Использовать notebook из `training/original/`.
5. При необходимости подключить код из `training/reconstructed/`.
6. Сопоставить результаты с сохранёнными файлами из `runs/`.
7. Проверить полученные веса по `artifacts/manifest.json`.

Для кандидатов, исходный самостоятельный training-скрипт которых не сохранился, репозиторий содержит восстановленный код из выполненного notebook и его outputs. Этот статус явно указан в метаданных и документации.

## Запуск runtime

Перед запуском необходимо поместить файлы модели в директорию, ожидаемую выбранным runtime. Точный путь указан в README соответствующего кандидата.

Общий контракт запуска:

```bash
python run.py \
  --items-path /path/to/items.parquet \
  --matches-path /path/to/matches.parquet \
  --output-path /path/to/submit.csv
```

Для совместимости runtime также принимает исторические варианты аргументов с подчёркиваниями.

## Формат финального solution

Финальный inference-only ZIP содержит:

```text
solution/
├── metadata.json
├── run.py
├── models/
│   └── model-directory/
│       ├── config.json
│       ├── model.safetensors
│       └── tokenizer files
└── src/
    └── runtime code
```

`metadata.json` содержит:

* `image` — заранее опубликованный Docker-образ с необходимыми библиотеками;
* `entry_point` — команду запуска solution.

Docker-образ не входит в ZIP. К моменту запуска он должен быть доступен площадке по имени, указанному в `image`.

Исправленные сборщики кандидатов находятся в `construction/runtime/build_submit.py`. Они проверяют наличие файлов модели, SHA-256 весов и создают воспроизводимый ZIP без сетевых запросов.

## Ограничения воспроизводимости

В репозитории явно зафиксированы следующие ограничения:

* датасеты и большие веса не хранятся в Git;
* часть исторических training-checkpoint не была собрана;
* для отдельных запусков training-код восстановлен из выполненных notebook и outputs;
* полный runtime необходимо отдельно проверять с реальными весами в целевом контейнере;
* окончательный выбор двух финальных submission зависит от результата проверки площадкой.

Эти ограничения документируются явно и не скрываются за предположениями.
