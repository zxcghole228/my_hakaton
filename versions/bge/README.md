# BGE model family

В этой директории зафиксированы три кандидата семейства USER-BGE-M3, разработанные для задачи матчинга товаров E-CUP 2026.

Машиночитаемый перечень версий находится в [`registry.json`](registry.json).

## Кандидаты

| -: | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | -------------------: |
|  1 | [`01_base_bge_m3`](01_base_bge_m3/README.md)                                                         | Baseline fine-tuning предобученной `deepvk/USER-bge-m3`                                                  | `0.5136543845676982` |
|  2 | [`02_stage_b_v2_checkpoint_soup_8515`](02_stage_b_v2_checkpoint_soup_8515/README.md)                 | Stage B и checkpoint soup: `0.15 × step_00400 + 0.85 × step_02000`                                       | `0.5520634383301408` |
|  3 | [`03_stage_b_v3_cross_soup_symmetry_tta_5540`](03_stage_b_v3_cross_soup_symmetry_tta_5540/README.md) | Cross-checkpoint soup: `0.83 × Stage-B v2 step_02000 + 0.17 × Stage-B v3 step_00400`, затем symmetry TTA | `0.5539900397479464` |

Значения leaderboard являются результатами, сообщёнными командой. Связь каждого результата с конкретным файлом весов подтверждена автором модели и зафиксирована через SHA-256.

## Эволюция решений

### Кандидат 1: baseline

Первый кандидат получен дообучением открытой предобученной модели `deepvk/USER-bge-m3` на базовом корпусе матчей.

Это не обучение BGE со случайно инициализированными весами. Кандидат не использует checkpoint soup, ансамблирование или symmetry TTA.

### Кандидат 2: Stage-B v2 checkpoint soup

Второй кандидат продолжает baseline-направление с использованием ручной разметки, LLM replay и Stage-B обучения.

Финальные веса построены объединением двух checkpoint:

`0.15 × step_00400.pt + 0.85 × step_02000.pt`

После объединения используется одна модель и один прямой проход для каждой пары. Symmetry TTA на инференсе не применяется.

### Кандидат 3: Stage-B v3 cross-soup и symmetry TTA

Третий кандидат использует checkpoint из Stage-B v2 и checkpoint из Stage-B v3:

`0.83 × Stage-B v2 step_02000.pt + 0.17 × Stage-B v3 step_00400.pt`

На инференсе применяется symmetry TTA: модель оценивает оба порядка товаров, после чего вероятности усредняются.

## Базовая модель и лицензия

Все три кандидата основаны на [`deepvk/USER-bge-m3`](https://huggingface.co/deepvk/USER-bge-m3), опубликованной под лицензией Apache-2.0.

Точная ревизия базовой модели, использовавшаяся во время исходного обучения, не была записана и поэтому не восстанавливается предположением. Этот факт явно отмечен в метаданных версий.

Runtime загружает модель из локальной директории и не требует обращения к проприетарным inference API.

## Структура версий

Внутри каждой версии используются следующие каталоги и файлы:

* `README.md` — описание кандидата, его происхождения и ограничений воспроизводимости;
* `version.json` — машиночитаемые параметры обучения, метрики, lineage и сведения о весах;
* `training/original/` — исходные notebook и скрипты, полученные от автора;
* `training/reconstructed/` — восстановленный исполнявшийся код, если исходный файл не сохранился отдельно;
* `runs/` — сохранённые метрики, логи и результаты выбора checkpoint;
* `construction/original/` — исходный сборщик submission;
* `construction/runtime/` — исправленный воспроизводимый сборщик;
* `solution/original/` — неизменённый snapshot отправленного solution;
* `solution/runtime/` — исправленный runtime-код;
* `artifacts/manifest.json` — размеры, SHA-256 и статус доступности артефактов;
* `recovery/` — исходный восстановительный snapshot, если он требовался.

Некоторые каталоги присутствуют только у тех кандидатов, для которых соответствующие материалы сохранились.

## Original и runtime

`solution/original` сохраняет код в том виде, в котором он был получен от автора модели и использовался при подготовке исходного submission.

`solution/runtime` содержит исправления воспроизводимости и контракта запуска:

* поддержку аргументов как с дефисами, так и с подчёркиваниями;
* локальную загрузку модели без сетевых запросов;
* сохранение всех входных строк, включая пары с пустыми текстами;
* сохранение исходного порядка строк и повторяющихся пар;
* формирование столбца `predict`.

Leaderboard score относится к исходному отправленному solution. Для исправленного runtime тот же результат не заявляется без отдельного запуска на площадке.

## Веса моделей

Большие файлы весов не хранятся в Git. Для каждого кандидата в `registry.json`, `version.json` и `artifacts/manifest.json` указаны:

* ожидаемое имя файла;
* размер в байтах;
* SHA-256;
* локальный путь;
* статус доступности.

Контрольные суммы финальных весов:

* кандидат 1: `d1c65bd374abf91cc8373bfee05b1c706c34acf0c8aa83e88e4f0a409ea20735`;
* кандидат 2: `d51bd8b0170a4a0d307d803050fa8aa1bc525fd2780e8b4faef6a13e8c6e3d93`;
* кандидат 3: `b9d98750751a2442a946f6d9188fa3cda251df4d818ad0b23fa13abf223469da`.

## Данные

Датасеты соревнования и большие промежуточные артефакты не включены в Git.

Для полного воспроизведения необходимо отдельно предоставить соответствующие файлы данных, перечисленные в `version.json` каждой версии. Репозиторий не маскирует отсутствующие данные или checkpoint: их статус явно указан как локальный либо `not_collected`.
