# Соответствие требованиям E-CUP 2026

Этот документ описывает соответствие репозитория требованиям финальной проверки задачи «Матчинг товаров» E-CUP 2026.

Документ относится только к BGE-решениям задачи матчинга товаров. Решения других треков должны проверяться отдельно.

## Краткая сводка

| Требование                                              | Состояние                                              | Подтверждение в репозитории                                                 |
| ------------------------------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------- |
| Решение создано во время E-CUP 2026                     | Зафиксировано заявлением команды и историей разработки | Git history, source snapshots, notebook outputs, run logs                   |
| Отсутствуют проприетарные модели и inference API        | Выполнено для представленных BGE-кандидатов            | Открытая базовая модель, локальный runtime, отсутствие сетевых вызовов      |
| Код обучения воспроизводим                              | Условно выполнено                                      | Notebook, training-скрипты, reconstructed source, параметры и environments  |

## Период разработки

Команда заявляет, что solution-specific код обучения, preprocessing, построения checkpoint soup и инференса был создан и использован в период проведения E-CUP 2026.

Внешними компонентами являются:

* базовая предобученная модель;
* открытые программные библиотеки;
* датасеты соревнования;
* Docker-образ среды организаторов.

Они не выдаются за созданные командой.

История разработки сохраняется через:

* Git commits;
* исходные notebook;
* восстановленные snapshots;
* outputs выполненных запусков;
* training logs;
* метрики;
* контрольные суммы файлов.

## Базовая модель

Все три кандидата используют:

```text
deepvk/USER-bge-m3
```

Источник:

```text
https://huggingface.co/deepvk/USER-bge-m3
```

Лицензия модели:

```text
Apache-2.0
```

Точная ревизия базовой модели, использованная при исходном обучении, не была сохранена. В метаданных она отмечена как `missing` или `not_recorded`. Репозиторий не подменяет неизвестную ревизию предположением.

## Программные зависимости

Основной стек включает:

* Python;
* PyTorch;
* Transformers;
* NumPy;
* pandas;
* PyArrow;
* scikit-learn;
* tqdm.

Training-окружение и известные версии библиотек описаны в:

```text
requirements/README.md
requirements/training-cu124.txt
versions/bge/<candidate>/training/environment.json
```

Runtime не обращается к платным или закрытым inference API. Модель и tokenizer загружаются из локальной директории.

## Данные и разметка

Репозиторий использует существующие локальные датасеты соревнования:

* `items.parquet`;
* `items_human.parquet`;
* `matches.parquet`;
* `matches_llm.parquet`.

`matches_llm.parquet` рассматривается как готовый входной корпус. Репозиторий не запускает внешний LLM API для повторной генерации labels.

`matches.parquet` содержит ручную разметку, используемую на Stage B.

Собственная дополнительная LLM-разметка для представленных BGE-кандидатов не выполнялась. Поэтому отдельный pipeline внешнего relabeling отсутствует и не требуется для повторения описанных запусков.

Preprocessing товарных текстов сохраняется в коде `pair_text_v1` и доступен в исходных и runtime-копиях.

Датасеты не публикуются в Git из-за размера и условий распространения. Их ожидаемая структура описана в [`data/README.md`](../data/README.md).

## Воспроизводимость обучения

Для кандидатов сохранены:

* исходные training notebook;
* самостоятельный training-скрипт baseline-кандидата;
* reconstructed training-код Stage-B кандидатов;
* параметры обучения;
* seeds;
* параметры разделения данных;
* preprocessing;
* training environment;
* логи;
* метрики;
* checkpoint selection;
* формулы checkpoint soup.

Для Stage-B запусков часть исходного кода была восстановлена из выполненных notebook и outputs. Такие файлы находятся в `training/reconstructed/`, а исходный восстановительный snapshot — в `recovery/`.

Репозиторий позволяет изучить и повторно запустить pipeline при наличии необходимых данных, базовой модели и стартовых checkpoint.

При этом репозиторий сам по себе не гарантирует побитовое воспроизведение финальных весов, поскольку:

* точная ревизия базовой модели не записана;
* некоторые исторические checkpoint не собраны;
* большие данные и веса не хранятся в Git;
* распределённые GPU-операции могут быть недетерминированными;
* полный freeze транзитивных зависимостей не сохранился.

Эти ограничения явно документируются и не скрываются.

## Прослеживаемость весов

Для каждого финального `model.safetensors` сохранены:

* размер;
* SHA-256;
* кандидат;
* локальный путь;
* статус хранения;
* связь с leaderboard submission.

Основные сведения находятся в:

```text
versions/bge/registry.json
versions/bge/<candidate>/version.json
versions/bge/<candidate>/artifacts/manifest.json
```

Большие веса игнорируются Git, но могут находиться в локальной рабочей копии.

## Original и исправленный runtime

`solution/original` содержит исторический solution без содержательных изменений.

`solution/runtime` содержит исправления контракта запуска и устойчивости:

* поддержку CLI-аргументов с дефисами;
* сохранение совместимости с историческими аргументами;
* локальную загрузку модели;
* сохранение всех входных пар;
* сохранение порядка строк и дубликатов;
* корректное создание столбца `predict`.

Публичный leaderboard score относится к исходному submission. Исправленному runtime не приписывается тот же результат без отдельного запуска на площадке.

## Формат финального solution

Финальный inference-only ZIP содержит:

* `metadata.json`;
* `run.py`;
* runtime-код;
* tokenizer;
* config модели;
* `model.safetensors`.

`metadata.json` использует поля:

```text
image
entry_point
```

Во всех представленных исходных solution указан образ:

```text
odsai/ecup26-matching-baseline:1.0
```

и точка входа:

```text
python -u run.py
```

Docker-образ должен быть доступен площадке отдельно. Dockerfile не включается в inference-only ZIP.

## Проверки перед финальным выбором

Перед фиксацией двух финальных решений необходимо:

1. Убедиться, что оба submission успешно завершились на стороне платформы.
2. Проверить, что для них был рассчитан private leaderboard.
3. Сопоставить submission с SHA-256 весов.
4. Проверить доступность Docker-образа из `metadata.json`.
5. Зафиксировать SHA-256 полных submission ZIP.
6. Обновить `versions/bge/registry.json`.
7. Обновить поле `selection` в `version.json`.
8. Создать итоговый документ в `final/`.
9. Выполнить финальную проверку Git на отсутствие весов, данных и секретов.

До завершения этих действий ни один кандидат не помечается как окончательно выбранный.
