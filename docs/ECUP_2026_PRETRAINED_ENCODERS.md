# E-CUP 2026 — Параллельный трек: дообучение готового энкодера

Альтернатива треку «свой токенизатор + MLM с нуля» (см. `ECUP_2026_MATCHING.md`).
Здесь: берём готовый предобученный энкодер и дообучаем в cross-encoder.

**Зачем вести оба трека параллельно.** Custom-MLM — это ~1.5 суток GPU только на претрейн,
до первого сабмита. Этот трек даёт рабочий сабмит на лидерборде **за день**, служит
референсной точкой («окупает ли custom-MLM свою цену?») и страховкой, если претрейн не взлетит.
Вся обвязка — нормализация, извлечение сущностей, `[DIFF]`-вход, две головы, валидация
по компонентам связности — **общая для обоих треков**. Меняется только backbone.

---

## 1. Кандидаты

Ключевая величина для скорости — **не общее число параметров, а параметры тела энкодера**
(без эмбеддингов). Эмбеддинги не участвуют в матричных умножениях по слоям, они только
занимают память и время загрузки. У многоязычных моделей на XLM-R словарь 250k раздувает
общий счётчик, вводя в заблуждение.

| Модель | Всего | Тело (без emb) | Слоёв × hidden | Vocab | Роль |
|---|---|---|---|---|---|
| `cointegrated/rubert-tiny2` | 29M | ~12M | 3 × 312 | 84k | Day-1 baseline, отладка пайплайна |
| `sergeyzh/rubert-mini-frida` | ~32M | ~15M | 7 × 312 | 84k | Лучше tiny2 при той же скорости |
| `ai-forever/ruBert-base` | 178M | ~86M | 12 × 768 | 120k | **Основной рабочий вариант (RU)** |
| `DeepPavlov/rubert-base-cased` | 178M | ~86M | 12 × 768 | 120k | Альтернатива ruBert-base |
| `intfloat/multilingual-e5-base` | 278M | ~86M | 12 × 768 | 250k | **Основной рабочий вариант (multi)** |
| `intfloat/multilingual-e5-large` | 560M | ~303M | 24 × 1024 | 250k | Тяжёлый, но проходит по времени |
| `BAAI/bge-m3` | 568M | ~303M | 24 × 1024 | 250k | То же тело, лучше retrieval-претрейн |

топ-15 отдаёт исходники на проверку жюри.

## 2. Проходят ли они по времени

FLOPs на пример ≈ `2 × P_тела × seq_len`. При seq 192 и реальных ~400 TFLOPS на H100 (bf16):

| Класс | GFLOP/пример | Пар/с (реалистично) | 275k пар | ×2 swap-TTA |
|---|---|---|---|---|
| tiny (12M) | 4.6 | 60–80k | ~4 с | ~8 с |
| base (86M) | 33 | 5–8k | 35–55 с | 70–110 с |
| large (303M) | 116 | 2–3k | 90–140 с | 180–280 с |

При бюджете Private 780 с **проходит даже large со swap-TTA**, и остаётся место под ансамбль
`large + base` (~350 с суммарно). То есть по throughput вы не ограничены — выбирайте модель
по качеству.

**Реальное ограничение — Check: 1000 пар за 1 минуту.** Там доминирует фиксированный оверхед:

```
import torch                 ~8–12 с
import transformers          ~5–8 с
чтение parquet               ~3–5 с
загрузка весов large fp16    ~5–10 с (холодный page cache!)
─────────────────────────────────────
итого до первого батча       ~25–35 с из 60
```

Отсюда правила: веса в **fp16 на диске** (вдвое меньше читать), **safetensors + mmap**,
импортировать `transformers` лениво или вообще собрать модель на голом `torch`,
**никакого `torch.compile`**.

**Стоимость обучения** (1×H100, bf16, seq 192, fwd+bwd ≈ 3× fwd):

| Модель | Стадия A: 11M LLM-пар, 1 эпоха | Стадия B: 365k human, 1 эпоха |
|---|---|---|
| tiny | ~7 мин | ~15 с |
| base | ~45–60 мин | ~2 мин |
| large | ~2.5–3 ч | ~7 мин |

Полный цикл на base — **2 эпохи A + 4 эпохи B ≈ 2 часа**. Это и делает трек привлекательным:
можно перебрать 5–6 конфигураций за сутки.

## 3. Лестница экспериментов

**День 1 — `rubert-tiny2`.** Цель не качество, а прогон всего пайплайна насквозь: parquet →
нормализация → токенизация → обучение → инференс → csv → Docker → сабмит. Получаете первую
точку на лидерборде и, главное, **проверяете тайминги на Check**. Обучение занимает минуты,
поэтому все баги вылезают дёшево.

**День 2 — `ruBert-base` и `multilingual-e5-base`, обе.** Одинаковый рецепт, сравниваете
по macro-AP на своей валидации. Здесь же меряете fertility обоих токенизаторов на своём
корпусе — это предскажет, кто выиграет, ещё до обучения.

**День 3 — победивший base с полным рецептом** (`[DIFF]`-вход, флаги-токены, две головы,
cat-balanced sampling, swap-TTA). Это ваш рабочий сабмит.

**День 4+ — large** (`bge-m3` / `e5-large` / `sbert_large_nlu_ru`) и ансамбль
`large + base + CatBoost` через rank-average внутри категории.

## 4. Обрезка словаря (vocab trimming)

Самый выгодный трюк этого трека. У XLM-R-based моделей (e5, bge-m3) словарь 250k:

| Модель | Эмбеддинги | После обрезки до 64k | Экономия на диске (fp16) |
|---|---|---|---|
| `e5-base` | 250k × 768 = 192M | 49M | 278M → 135M, ~290 МБ |
| `bge-m3` / `e5-large` | 250k × 1024 = 256M | 65M | 568M → 368M, ~400 МБ |

Что это даёт: **вдвое быстрее загрузка весов** (главный риск на Check), меньше архив
(лимит 5 ГБ — критично для ансамбля из трёх large), больше места под батч.
На качество влияет пренебрежимо: вы выбрасываете токены тайского, хинди и корейского,
которых в русском e-commerce нет.

```python
from collections import Counter
import torch, json

# 1. частоты токенов на своём (уже нормализованном!) корпусе
cnt = Counter()
for batch in corpus_batches(3_000_000):
    for enc in tok(batch, add_special_tokens=False)["input_ids"]:
        cnt.update(enc)

# 2. отбираем покрытие 99.9% вхождений + спецтокены + ВСЕ одиночные символы
total, acc, keep = sum(cnt.values()), 0, set(tok.all_special_ids)
keep |= {i for i, t in enumerate(tok.convert_ids_to_tokens(range(len(tok))))
         if len(t.lstrip("▁##")) <= 1}          # страховка от UNK-взрыва
for tid, c in cnt.most_common():
    keep.add(tid); acc += c
    if acc / total > 0.999: break
keep = sorted(keep)

# 3. новая матрица эмбеддингов
old = model.get_input_embeddings().weight.data
model.resize_token_embeddings(len(keep))
model.get_input_embeddings().weight.data.copy_(old[keep])
```

Шаг 4 — пересборка самого токенизатора: у Unigram (XLM-R) фильтруете `vocab` в
`tokenizer.json` с сохранением scores, у BPE — ещё и `merges`, выбрасывая правила,
ссылающиеся на удалённые токены. Фидлово; **обязательно** проверьте после: доля `<unk>`
на held-out корпусе должна быть ~0, а токенизация 10k случайных карточек должна совпасть
с исходной по числу токенов ±1%.

> Если времени нет — пропустите обрезку. Это оптимизация загрузки и размера, а не качества.
> Часть RU-адаптированных моделей (линейка `deepvk/`, `sergeyzh/`) уже идёт с урезанным
> словарём — проверьте `len(tokenizer)` прежде чем делать работу руками.

## 5. Добавление доменных токенов

Готовый токенизатор рвёт `SM-A515F` и `1500ml` на куски — это главный минус трека
относительно custom-BPE. Частичная компенсация без переобучения токенизатора:

1. **Структурные спецтокены** — `[CAT] [BRAND] [NAME] [ATTR] [DESC] [DIFF] [A] [B]` и
   флаги-детерминанты `[BRAND_NE] [MODEL_NE] [QTY_NE] [UNIT_NE] [COLOR_NE] [EAN_EQ]`.
2. **Частые канонические единицы** из нормализации — `128gb`, `256gb`, `500ml`, `1500ml`,
   `1000w`. Отберите 2–5k самых частых по корпусу.

Инициализация новых эмбеддингов — **средним по сабтокенам исходного разбиения**, не случайно.
Случайная инициализация ломает первые сотни шагов и на коротком файнтюне не восстанавливается:

```python
new_tokens = SPECIALS + top_unit_tokens
sub = [tok(t, add_special_tokens=False)["input_ids"] for t in new_tokens]  # ДО add_tokens
tok.add_tokens(new_tokens)
model.resize_token_embeddings(len(tok))
W = model.get_input_embeddings().weight.data
for t, ids in zip(new_tokens, sub):
    W[tok.convert_tokens_to_ids(t)] = W[ids].mean(0)
```

Меряйте fertility до и после — если прирост меньше 5%, добавленные токены не окупают
раздутый словарь.

## 6. Рецепт файнтюна

Идентичен основному треку — меняется только backbone:

- **Стадия A**: 11M LLM-меток, soft targets, `head_llm`, LR 1e-4 (для large 5e-5), 2 эпохи, cosine.
- **Стадия B**: 365k human, `head_human`, LR 2e-5, **layer-wise decay 0.9**, EMA, 3–5 эпох,
  category-balanced sampling `1/sqrt(n_cat)`, swap-аугментация,
  ранняя остановка по macro-AP.

Три отличия, специфичных для готовых моделей:

**Layer-wise decay здесь важнее.** У предобученной модели в нижних слоях лежит языковое знание,
полученное на корпусах, которых у вас нет. Агрессивный LR его стирает — а восстановить нечем.
Для large берите decay 0.85 и первые 2 слоя замораживайте совсем.

**Warmup длиннее.** 5–10% шагов против обычных 2–3%: новые головы и добавленные эмбеддинги
на старте дают большие градиенты в тело модели.

**Pooling — по тому, как модель обучалась.** `bge-m3` — CLS, `e5-*` — mean pooling,
`rubert-tiny2` — mean. Для cross-encoder разница невелика, но начинать надо с «родного»
варианта, иначе первые эпохи уходят на переучивание пулинга.

## 7. Двойное использование: bi-encoder бесплатно

`e5` и `bge-m3` предобучены под retrieval, поэтому у них **осмысленный zero-shot косинус**
ещё до всякого дообучения. Используйте это в двух местах:

1. **Фича для CatBoost**: косинус + поэлементные `|a−b|` и `a*b`, сжатые в несколько компонент.
   Диверсифицирует ансамбль — bi-encoder ошибается не там же, где cross-encoder.
2. **Sanity-check валидации**: zero-shot косинус должен давать заметно выше случайного macro-AP.
   Если нет — у вас баг в сплите или в чтении данных, и это надо чинить до всякого обучения.

Внимание: `e5` требует префиксы `query:` / `passage:` — без них качество как bi-encoder падает
ощутимо. При использовании в cross-encoder префиксы не нужны.

Стоимость: эмбеддинги считаются по **уникальным товарам**, а не по парам. При ~400k уникальных
товаров на 275k пар это сопоставимо с одним проходом cross-encoder — то есть в бюджет
влезает, но не бесплатно.

## 8. Ансамбль и финальный сабмит

Смешивать **rank-average внутри каждой категории** (метрика ранговая, среднее сырых скоров
моделей с разной калибровкой хуже):

```python
sub["predict"] = 0.0
for cat, idx in sub.groupby("category").groups.items():
    r = sum(w * sub.loc[idx, c].rank(pct=True) for c, w in zip(cols, weights))
    sub.loc[idx, "predict"] = r
```

Разумный состав: `large cross-encoder (0.5) + base cross-encoder (0.3) + CatBoost на фичах (0.2)`.
Веса подобрать на валидации, но не переусердствовать — на 365k human-пар оптимизация весов
переобучается быстро; шаг сетки 0.1 достаточно.

**Два финальных решения**: одно максимальное по public (ансамбль + графовый пост-процессинг),
одно консервативное (одиночный cross-encoder без графа). Страховка от переобучения под public
при соотношении 30/70.

## 9. Когда этот трек побеждает custom-MLM

Считайте честно, а не по вере в «свою модель»:

| Сигнал | Вывод |
|---|---|
| Fertility готового токенизатора на вашем корпусе < 2.0 | Custom-BPE даст мало, оставайтесь на готовой модели |
| Fertility > 2.5 и seq_len упирается в 192 | Custom-BPE окупится, ведите оба трека |
| `large` уже упирается в macro-AP, а данные не исчерпаны | Проблема во входе/разметке, а не в backbone — не тратьте GPU на претрейн |
| Стадия A на 11M даёт большой прирост над стадией B в одиночку | Данных много, custom-претрейн скорее окупится |
| До дедлайна < 5 дней | Только этот трек. Custom-MLM не успеет дать сабмит |

Разумный итог для большинства сценариев: **дообученный `large` с полной обвязкой обычно
сильнее, чем свой маленький MLM с наивным входом.** Custom-претрейн выигрывает тогда,
когда обвязка уже выжата и упор идёт в длину последовательности.
